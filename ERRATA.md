# Errata

This file records known defects in published TrialDiff artifacts. Frozen
packages are never rewritten (see the immutability rule in
`EVIDENCE_RECORD_PRIMITIVE.md`); defects are corrected in new generations
under new rule-set hashes, and documented here.

## E1 — Spurious `why_stopped_removed_in_terminal_context` memberships (2026-07-14)

**Affected artifacts:** `event_class_records_v0.1` and `event_class_records_v0.1.1`
(byte-identical record sets), the live deployment rows generated by the
same code, **and the published Zenodo dataset**
[10.5281/zenodo.20816639](https://doi.org/10.5281/zenodo.20816639)
(v0.1.1; concept DOI 10.5281/zenodo.20801956, which also covers v0.1 at
10.5281/zenodo.20801957) together with its linked `trialdiff-public`
snapshot. Verified on 2026-07-14: all 100 record files in the Zenodo
v0.1.1 archive are byte-identical to this repository's
`event_class_records_v0.1.1/records/`, so this erratum applies to the DOI
dataset verbatim. Per the immutability rule, the Zenodo record is not
withdrawn or mutated; the correction ships as a new version (v0.1.2) under
the same concept DOI with this erratum attached.

**Defect.** 9 of the 13 records carrying the
`why_stopped_removed_in_terminal_context` event class do not evidence a
`whyStopped` change. Their own embedded patches — the registry's diff
between the two versions — contain no operation touching
`/protocolSection/statusModule/whyStopped`, so the field did not change
between those versions. The class fired because the TO-version snapshot was
not stored in the working database, and the predicate read the missing
snapshot as "field absent" (`trialdiff/event_classes.py`, predicate
`why_stopped_removed_in_terminal_context`; the missing snapshot came from
the LEFT JOIN in `trialdiff/db.py::iter_evidence_source_rows`). A storage
gap was reported as a registry change. The affected records assert, in
`claims_supported`, "The whyStopped field changed from nonempty to empty or
absent in a terminal-status context" — a claim their own patch contradicts.

**Affected records (spurious membership):**

- `evt_NCT04278144_v33_v34_bdd9f29ed71e` (the packages' three-class showcase record; two of its three classes stand)
- `evt_NCT05967286_v2_v3_4853c53774e8`
- `evt_NCT03130439_v15_v16_569889d76b15`
- `evt_NCT02154529_v23_v24_a89d33f8d488`
- `evt_NCT05243641_v19_v20_cea232b10ce3`
- `evt_NCT03535506_v8_v9_289490423374`
- `evt_NCT03094169_v12_v13_64ceb88d3746`
- `evt_NCT04588246_v18_v19_21a682b446f7`

**Genuine memberships (patch shows a real whyStopped removal):**
`evt_NCT00165256_v7_v8_38a2a576d1e0`, `evt_NCT01147016_v16_v17_ed2f5cc6917a`,
`evt_NCT03025035_v9_v10_1bcde1315533`, `evt_NCT01818063_v12_v13_0fae33fbeccc`.

**Corrected counts.** The published class count of 13 is therefore 4 under
the corrected definition; the package overlap distribution inherits the
error for this class. Other event classes are patch- or snapshot-anchored
and are not affected; in particular the v0.1.1 "Boundary Analysis" chain
(4,485 patches scanned → 73 inclusive primary-endpoint flags → 63
reconciliation-confounded → 10 clean class members) rests on patch-anchored
predicates and is expected to survive, but must be recomputed and
re-stated as part of the v0.1.2 regeneration rather than carried forward.

**Fix.** The missing-snapshot policy is now shared by all predicates:
when no TO-version record is stored, the TO view is derived by replaying
the registry's own adjacent-version patch over the FROM-version record
(`trialdiff/event_classes.py::derive_to_record`), so a storage gap can
never read as a field change; the whyStopped predicate additionally
accepts direct patch evidence when derivation is impossible. The prose
definitions were updated accordingly, which produces new rule-set hashes:

Because the TO view is now derived when a snapshot is missing, sibling

`why_stopped_removed_in_terminal_context` class (see `RELEASING.md` for the
regeneration and live-deployment steps; regeneration requires the private
working database and is an operator action).

## E2 — Wall-clock timestamp leaked into the event hash chain (2026-07-14)

**Defect.** `materiality_events.raw_hash` (surfaced in evidence records as
`materiality_event_hash`, inside the canonical payload) was computed over a
dict that included the `created_at` wall-clock stamp
(`trialdiff/classifier/materiality.py::provenance_for_event`). Re-running
`classify` on identical inputs at a different time therefore produced a
different `materiality_event_hash` and a different `canonical_hash` — the
classify→generate replay was not byte-reproducible, contrary to the
determinism guarantee in `EVIDENCE_RECORD_PRIMITIVE.md`.

**Fix.** Two leaks were closed. First, the hash is now computed over the
event's deterministic content only (`MaterialityEvent.content_dict()`,
which excludes `created_at`); `created_at` remains stored as unhashed
metadata. Second, an independent audit found the `categories` list broke
priority ties by set iteration order, making the hash
PYTHONHASHSEED-dependent across processes (reproduced: five fresh
`classify` runs on identical inputs produced two distinct hashes); ties
now break deterministically by category name. Replay is covered by
`tests/test_determinism.py`, including a cross-process,
cross-PYTHONHASHSEED assertion.

**Impact on frozen artifacts.** None retroactively: frozen records remain
valid snapshots of the hashes their generation produced. New generations
produce `materiality_event_hash` values that are reproducible from inputs
alone; hashes from re-classified events will differ from the frozen ones for
this reason in addition to any rule changes.

## E3 — "Severity means review priority" wording inside the frozen alpha package (2026-07-14)

`manual-audit-5-records.md` (pinned in `MANIFEST.sha256`) stated "Severity
means review priority, not proven wrongdoing" — the pre-calibration framing.
The v0.2/v0.2.1 calibration subsequently failed its pre-registered gate, and
severity was decoupled from review priority
(`SEVERITY_DECOUPLING_v0.2.1.md`); `VALIDATION.md` in the same package
already used the corrected framing, so the frozen package contradicted
itself. A superseded-wording banner has been added to
`manual-audit-5-records.md` and the manifest entry re-pinned (see the
manifest policy below). The audit's findings themselves are unaffected.

## Integrity is not correctness

Every hash and manifest in this project proves **byte integrity**: the
artifact you hold is bit-for-bit the artifact that was published. None of
them prove **semantic correctness**: that the claims inside the artifact
are true. E1 is the standing demonstration — the Zenodo v0.1.1 archive
passes every hash, manifest, and `trialdiff verify` check while containing
nine false class claims. Verification tooling answers "has this been
altered?"; errata and regeneration under new rule-set hashes answer "was
this right?". Both layers are needed, and conflating them overstates what
a passing check means.

## Manifest policy

`MANIFEST.sha256` pins two kinds of entries:

- **Record entries (`records/*.json`): immutable.** They are never re-pinned;
  a hash change there is a defect, full stop.
- **Documentation and tooling entries (`README.md`, `CLAIMS.md`,
  `manual-audit-5-records.md`, `scripts/*.py`, …): living.** When these
  evolve, their manifest entries are re-pinned in the same commit, and git
  history is the audit trail for previous states. Re-pins that accompany a
  correction are noted in this file.

Re-pinned on 2026-07-14 alongside E1–E3: `README.md`, `CLAIMS.md`,
`manual-audit-5-records.md`, `EVIDENCE_RECORD_SCHEMA.md`,
`EVIDENCE_RECORD_PRIMITIVE.md`, `scripts/export_alpha_demo.py`,
`scripts/validate_alpha_demo.py`. All 40 record entries are unchanged.
