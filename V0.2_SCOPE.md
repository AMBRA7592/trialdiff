# TrialDiff v0.2 Scope

Status: planning scope
Date: 2026-06-18

TrialDiff v0.2 moves from a bounded alpha evidence demo to a calibrated evidence engine with buyer-relevant outputs. It expands along three axes only: broader corpus, stronger validation, and a narrowly tested use case.

It does not reopen v0.1-alpha architecture.

## 1. Objective

The v0.2 objective is to test whether TrialDiff can produce reproducible, source-linked Evidence Records over a broader breast-cancer trial corpus, with review-priority labels that survive adversarial or independent calibration.

The target claim is:

> TrialDiff can produce reproducible, source-linked Evidence Records over a broader breast-cancer trial corpus, with audited severity calibration and selected case studies showing why these records matter for trial transparency, publication review, diligence, and pharma intelligence.

This is stronger than v0.1, but still bounded.

## 2. Corpus Target

The target corpus is a recovered or regenerated expanded breast-cancer corpus, ideally the originally planned 100-study corpus.

The corpus must be explicitly documented:

- inclusion criteria;
- exclusion criteria;
- number of trials;
- number of adjacent version patches;
- number of materiality events;
- number of generated Evidence Records;
- source date or ingestion date;
- any relaxation rules used to reach the corpus size.

The corpus is still not a representative sample of all ClinicalTrials.gov records unless a separate sampling design establishes that claim.

## 3. Import Strategy

The v0.2 serving/export model should avoid full snapshot bloat unless a page or evidence object actually requires it.

Import by default:

- trial metadata;
- version metadata;
- adjacent JSON Patches;
- materiality events;
- Evidence Records;
- source URLs;
- source hashes;
- rule set hashes;
- evidence version;
- provenance fields needed to reproduce and cite a record.

Do not import full historical snapshots into the serving database by default if they are not needed for the frontend or exported records. Full snapshots may remain in a local archival store or compressed archive.

The 791 MB SQLite issue should not dictate product architecture. It should be treated as a storage/export design problem.

## 4. Severity Calibration Method

The v0.2 credibility upgrade is severity calibration.

Calibration must use a frozen rubric before records are reviewed. The rubric should define, in plain language, what should count as `critical`, `high`, `medium`, `low`, and `administrative/uncategorized` review priority.

The calibration sample must be stratified, not drawn only from critical records:

- critical records;
- high records;
- medium records;
- low or administrative records where available;
- at least one sample from major rule families, including outcome, timeline, enrollment/status, and design/intervention changes.

Target sample size: 50-100 records.

The reviewer must not treat TrialDiff's existing severity as authoritative. Calibration review is two-stage:

1. The reviewer assigns review priority from the raw material only: changed paths, patch payload, timing context, and source provenance. TrialDiff's assigned severity and rules fired are hidden at this stage.
2. After the independent priority judgment is recorded, TrialDiff's assigned severity and rules fired are revealed for disagreement analysis.

This preserves the diagnostic value of rule attribution without letting the classifier's own reasoning anchor the independent judgment.

Independence mechanism must be labeled accurately:

- If a domain expert reviews the sample, describe it as external domain review.
- If no domain expert is available, describe it as adversarial model review against a frozen rubric.
- Do not imply external clinical validation unless it actually occurred.

The calibration report must include:

- sample construction;
- frozen rubric;
- review procedure;
- confusion table or equivalent tier-comparison summary;
- false positives;
- false negatives;
- ambiguous cases;
- categories that over-fire or under-fire;
- rule changes made after calibration, if any;
- new `rule_set_hash` for any revised classifier.

Deliverable: `SEVERITY_CALIBRATION_v0.2.md`.

## 5. Stop Conditions

The buyer-facing brief is blocked unless severity calibration passes a pre-registered threshold.

Minimum pass threshold:

- false-positive rate among records labeled `critical` must be below 20%;
- false-positive rate among records labeled `critical` or `high` combined must be below 25%;
- no whole rule category may be found systematically mis-tiered;
- no unresolved source/provenance failure may affect a flagship candidate;
- no manuscript-disclosure or misconduct claim may be made without independent document review.

Rationale: v0.2 is still an evidence-engine calibration release, not a clinical validation study. The thresholds are strict enough to block a visibly over-firing classifier while allowing a conservative research artifact to proceed to a carefully vetted brief prototype.

If these thresholds are not met, v0.2 work pauses for rule revision and reclassification. The buyer-facing brief must not be sent as a recurring intelligence product until the revised rule set is recalibrated.

If calibration changes rules, v0.2 records must carry a new `rule_set_hash`. The v0.1-alpha package remains frozen and should not be retro-edited to match v0.2 rules.

## 6. Flagship Case Criteria

Flagship case studies must be selected from records that survive the same claim discipline as v0.1:

- registry change is real;
- timing context is clear;
- source links are durable enough for review;
- changed paths are inspectable;
- rules fired are explainable;
- claims supported and claims not supported are explicit;
- no manuscript-disclosure claim is made unless independently verified;
- no misconduct, intent, or regulatory-compliance claim is made.

NCT01275677 is a candidate for v0.2, not a v0.1-alpha case. It should only become a flagship if the Evidence Record survives source, timing, and claim-boundary checks.

Target: shortlist three flagship candidates, then publish two.

## 7. Buyer-Facing Brief Prototype

The buyer-facing artifact is not a SaaS dashboard. It is a short recurring evidence brief powered by TrialDiff.

Working title: `Clinical Trial Change Intelligence Brief` or `Pharma Delta Brief`.

First prototype:

- 5-10 high-priority trial changes;
- each item linked to a source-backed Evidence Record;
- one-paragraph interpretation;
- explicit non-claims;
- clear corpus scope;
- clear statement that severity means review priority;
- PDF or Markdown format.

The brief must have its own claims/non-claims contract because it adds interpretation beyond the Evidence Record itself.

Brief items must individually satisfy the Section 6 flagship criteria. Passing the aggregate calibration threshold is not enough to include a record in the brief.

The brief is contingent on severity calibration passing Section 5.

## 8. Out of Scope

Do not build:

- login;
- accounts;
- payments;
- alerts;
- generalized monitoring;
- broad dashboards;
- all-disease expansion;
- manuscript-disclosure claims without separate review;
- misconduct detection;
- sponsor-intent inference;
- DOI infrastructure for every intermediate package;
- architecture changes to v0.1-alpha.

Zenodo or DOI publication may be considered after v0.2 has a broader corpus and completed calibration.

## 9. Thirty-Day v0.2 Target

Output: `TrialDiff v0.2 Expansion Plan + Calibration Slice`.

Deliverables:

- this scope file finalized;
- recovered, regenerated, or explicitly redesigned expanded breast-cancer corpus path;
- selective import/export strategy;
- frozen severity-calibration rubric;
- stratified 50-record calibration sample;
- first draft of `SEVERITY_CALIBRATION_v0.2.md`;
- shortlist of three flagship candidate cases, including NCT01275677 if supported.

No frontend expansion unless needed to display records already generated by the engine.

## 10. Sixty-Day v0.2 Target

Output: `TrialDiff v0.2 Evidence Expansion Release Candidate`.

Deliverables:

- expanded corpus live or frozen;
- updated Evidence Record export;
- updated manifest;
- severity-calibration report;
- two flagship case studies;
- README v0.2 status update;
- release note;
- one sample buyer-facing brief if, and only if, calibration passes.

## 11. Ninety-Day Pilot Target

Output: `Clinical Trial Change Intelligence Brief pilot`.

Deliverables:

- two to four brief issues;
- narrow recipient list;
- one public sample issue;
- private version if needed;
- feedback from at least five relevant readers.

Target reader types:

- clinical-trial transparency researchers;
- medical writers;
- regulatory intelligence professionals;
- pharma diligence or competitive-intelligence readers;
- journal or reporting-methods reviewers.

The day-90 question is not whether the app is nicer. It is whether people with real workflows want repeated access to these evidence objects and interpretations.
